## 프로젝트 전제
- 이 저장소는 **하네스 개발용**이다. 구축 결과물은 다른 프로젝트(대상 프로젝트)에 복사해서 적용한다.
- 대상 프로젝트 전용 설정은 이 저장소에 적용하지 않는다. 대신 `README.md`의 "대상 프로젝트 적용 가이드"에 Stage별로 추가한다.
  - 예: GitHub 라벨, 브랜치 보호, Secrets, `.github/` 파일, CODEOWNERS 계정
- 이전 Stage와 연결되어야 한다. 이전 산출물을 입력으로 받고, 같은 `intent/<id>/` 경로를 사용한다.

## 구축 절차
1. **계획서 작성**: `.aisdlc/docs/reference/plan/stage-{{N}}-{{stage_name}}.md`
2. **승인 요청**: 나에게 계획 승인을 받기 전에는 구축하지 않는다. 내가 수정을 요청하면 계획서를 고친 뒤 다시 승인을 받는다.
3. **구축**: subagent에게 **계획서 파일만** 제공해서 구축하도록 지시한다.
   - 계획서의 파일 명세(역할, 핵심 규칙, 처리 흐름, 인터페이스)를 충족하도록 파일을 구현한다.
   - 계획서에 없는 작업은 하지 않는다: GitHub 설정, push, PR, commit
   - 구현 중 명세를 바꿔야 하면(규칙·인터페이스·흐름 변경) 계획서 명세에도 반영한다. 구현 세부 사항만 바뀐 경우는 반영하지 않는다.
   - 모두 통과하면 계획서 상태를 `구축 완료`로 바꾸고 완료 기준을 체크한다.
4. **완료 보고**: subagent 보고 내용을 이 세션에 보여준다. 단위 테스트는 내가 직접 다시 실행해 확인한다.
   - 보고 항목: 생성·수정 파일 / 테스트 결과(PASS·FAIL 수, 주요 출력) / 계획서 대비 변경 / 미해결 이슈 / `git status`
5. **커밋**: 내가 지시할 때만 현재 브랜치({{브랜치명}})에 커밋한다. push는 하지 않는다.

## 계획서 필수 구성
1. 목표: 블로그 요구사항 → 구현 매핑 표
2. 범위: 포함 / 제외(후속 Stage, 대상 프로젝트 설정)
3. 설계: 워크플로 다이어그램, 상태 전이, 저장 규칙, 통제 구성(권고/결정), 검증 규칙
4. 파일 목록: 생성·수정·삭제할 **모든** 파일(번호, 작업, 경로, 역할). 삭제가 없으면 "없음"이라고 명시
5. 파일 명세: 각 파일의 **전체 코드가 아니라 핵심 내용과 처리 흐름**을 적는다.
   | 파일 유형 | 작성할 내용 |
   |-----------|-------------|
   | 스킬 (`SKILL.md`) | frontmatter(`name`, `description` 트리거 조건), 모드, 단계별 절차, 금지 규칙 |
   | 템플릿 | frontmatter 키, 섹션 목록·순서, 섹션별 작성 기준 |
   | 스크립트·훅 | 목적, 사용법(인자), 입력(stdin JSON 필드 등), 처리 흐름, 검증·차단 규칙, 출력, 종료 코드 |
   | 설정 (`settings.json`, CI) | 등록할 이벤트·matcher·명령, 트리거 조건, job 구성 |
   | 테스트 | 케이스 표(이름, 입력·결함, 기대 결과) |
   | 문서 (`CLAUDE.md`, `README.md`) | 추가할 섹션과 항목 |
   - 형식이 정확해야 하는 부분만 짧은 코드 조각으로 넣는다: frontmatter 예시, 정규식, JSON 키 구조, 명령어
6. 구축 순서: 실행 권한 부여 포함
7. 테스트: 명령, 통과 기준
8. 완료 기준: 체크박스
- `README.md` 수정분에는 해당 Stage의 "대상 프로젝트 적용 가이드"를 포함한다(복사할 파일 표, 복사 스크립트, GitHub 설정, CLAUDE.md 추가 규칙, 확인 방법).

## 설계 원칙 (이전 Stage와 동일)
- **권고와 강제를 겹쳐 둔다**: 스킬은 권고에 그치므로, 반드시 지켜야 할 규칙은 훅·스크립트·CI로 강제한다.
- **에이전트는 자기 산출물을 스스로 승인하지 못한다**: 승인 상태 변경은 훅으로 차단하고, 승인은 PR에서 사람이 한다.
- **산출물 검증 스크립트를 하나로 공용**한다(훅 PostToolUse, CI, 사람 모두 같은 스크립트 사용).
- 스킬에는 **비대화형 모드**를 둔다(`claude -p`나 자동화에서 질문 없이 실행).
- 지표: 블로그에 나온 선행·후행 지표를 git·gh로 측정하는 스크립트를 둔다.
- 셸 스크립트는 **macOS bash 3.2 호환**(연관 배열·mapfile 금지)이며 `jq`를 사용한다.

## 테스트 요구사항
- `.aisdlc/tests/stage-{{N}}/run.sh`: `mktemp`로 격리한 환경에서 `check <이름> <기대 종료 코드> <명령>` 형식으로 실행하고, 마지막에 `PASS n / FAIL n`을 출력한다.
  - 검증 스크립트: 정상 1건 + 규칙마다 결함 하나씩 넣은 실패 케이스
  - 훅: 훅 입력 JSON을 흉내 내서 차단·허용·대상 외 파일·검증 피드백 확인
  - 설정 연결: settings.json 등록 여부, 스킬 파일 존재, 실행 권한
  - E2E(`E2E=1`): `claude -p`로 스킬을 비대화형 실행 → 산출물 검증 → 생성물 자동 삭제
- 구축 후 테스트가 다루는 범위와 다루지 않는 범위를 구체적으로 설명한다.

## 문서 작성 규칙
- 풀어서 설명하지 않고, 표·목록·코드 블록으로 가독성 좋게 정리한다.
- 핵심 내용은 정확하고 구체적으로 쓰되 너무 길게 풀어 쓰지 않는다.
- 생성·수정·삭제할 모든 파일을 빠짐없이 적는다.
- 해당 문서만 보고 구축할 수 있도록 작성한다. 전체 코드 대신 명세(핵심 규칙·흐름·인터페이스)만으로 구현할 수 있어야 한다.
- 한국어로 작성한다. 산출물 템플릿의 섹션명은 영어로 써서 기계가 읽을 수 있게 한다.
